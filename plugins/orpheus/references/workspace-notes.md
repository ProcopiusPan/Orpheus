# 项目工作区与研究笔记

用户应先在 Codex 中选择一个本地项目文件夹，再从该项目进入工作模式。这个项目文件夹是研究笔记的归属位置；Orpheus 安装目录只保存插件代码、隔离的候选、审查和正式 Fact。不要把普通笔记写进 Orpheus 安装目录，也不要把 Fact 复制成可编辑的第二份事实库。

## 多问题结构

默认在当前项目根目录建立：

```text
papers/
├── Author-Year-ShortTitle.md
└── Author-Year-ShortTitle.pdf  # 可选：手动原文或 Zotero 硬链接
Orpheus研究/
├── 研究索引.md
├── 问题一/
│   ├── 问题与进展.md
│   ├── 证明草稿.md
│   ├── 文献与证据.md
│   └── 提交与审查.md
└── 问题二/
    └── ...
```

使用简短、稳定、用户可辨认的问题文件夹名；重名时补充数学对象或日期，不覆盖既有问题。`研究索引.md` 链接每个实际存在的问题入口，并标注进行中、受阻、已有候选或已接纳等当前状态。

`papers/` 是当前项目多个数学问题共享的文献信息登记层和用户手动添加特定文献的入口；不要为每个问题另建 `papers/`。若当前环境配置了 Zotero，可把它用作全局书目、全文、附件和批注库；也可以直接使用项目 `papers/`、合法检索和可核验来源，研究不依赖 Zotero。项目通常保留同 stem 的 `.md` sidecar/阅读入口，Zotero 登记可选同一数据的硬链接或不复制附件的路径引用。用户手动放入原文时，使用稳定可读文件名（建议 `Author-Year-ShortTitle.ext`，冲突时追加版本或 arXiv 号），旁边配套 `.md`，记录标题、作者、年份、版本、原始 URL/DOI/arXiv、下载或核对日期、许可/访问说明、引用它的问题和来源登记状态。完整性摘要由登记或同步脚本自动生成和维护，用户只需提供真实文件；已有文件不覆盖，不重复下载。付费墙、登录、验证码或下载失败不得绕过；记录检索路径和缺失材料，未核对原文的文献不能进入候选 `sources`。

元数据 sidecar 可复制 [文献元数据模板](paper-metadata-template.md)。把真实原文或已选附件交给登记/同步脚本，由脚本生成完整性摘要并写入 sidecar；纯路径登记不在 `papers/` 复制全文。后续检查会重新计算并报告实际文件变化，不静默覆盖既有摘要。

使用 Zotero 时，按[文献归类](literature-management.md)顺手维护主库集合；`papers/` 保存项目书目和阅读入口，条目键用于关联主库，集合键或路径可按导航需要补充。归类可以在后续使用中修改，不增加单独审查、变更报告或全库扫描。

新问题启动或新结构出现时，按[文献探索与分析](literature-analysis.md)跨领域检索已有工作，在问题级 `文献与证据.md` 简记实际检索范围、结构别名、关键来源和待证桥接。发现有用文献后，在同一 sidecar 补充论文整体贡献、相关与更强结果、假设及 locator、已读与未读范围。Leader 在 `问题与进展.md` 记录已有工作覆盖范围、当前贡献定位及对路线的影响。登记成功或某个引用已核验，不代表整篇文献已充分阅读；无需为每次检索或扩展阅读新建文件。

需要吸收方法时，论文 sidecar 保存作者的研究动机、关键选择理由及来源，标清哪些是作者说明、哪些是 Reader 的重建。跨论文综合与当前问题的迁移建议写入已有 `文献与证据.md` 的“研究动机与方法迁移”部分，保留条件差额和下一步试探；Leader 将实际采用的路线调整记入 `问题与进展.md`。不固定增加新文件或综述表单。

每个问题先创建 `问题与进展.md`，它只保存题目、当前可靠结论、未解决事项和下一步，作为唯一续接入口。只有出现相应内容时才创建其余文件：`证明草稿.md` 保存推导正文和暂定论证；`文献与证据.md` 保存来源、locator 与实际阅读状态；`提交与审查.md` 只保存候选或 Fact ID、简短断言、状态和链接，不复制整份证明或审查报告。失败路线可在进展文件中简要保留；内容较多时再建立 `失败路线.md`。不要为每次工具调用、脚本运行或子代理另建文档；外部进度记录只在产生可交接里程碑时更新，并链接回上述文件。

`提交与审查.md` 对每个在审候选记录摘要、审查子代理或任务标识、启动时间和当前状态。冷审异步运行期间，依赖该候选的草稿必须标记“暂定，等待候选接纳”；Verifier 返回后立即更新 verdict、Fact ID 或返工状态，避免上下文压缩后遗忘待回收审查。

## 及时写入与续接

开始或恢复研究时，先读取项目的研究索引、该问题的入口笔记和相关 Fact。出现实质引理、反例、计算结论、路线改变或子代理可复用结果后，及时更新对应笔记；在长任务压缩、暂停、交接、候选提交和任务结束前再次写入。不要让唯一可复用结果只存在于对话历史。

### 当前状态与已有覆盖

`问题与进展.md` 维护一处可辨认的当前可靠结论、剩余问题和下一行动，原位更新；历史阶段另留简短记录与链接，不连续堆叠多份都自称“当前有效状态”的段落。已有计划和报告可以保留历史，但明确链接这一个续接入口。

主要路线的[覆盖判断](literature-analysis.md)链接到实际 Fact 版本或已核文献定理，说明可直接复用的部分和确切待证差额。发现内部已完成或外部更强先例后，同步修正当前计划、进展入口及相关的开放问题列表：删除其当前待办身份，标为已解决／已有结果覆盖并给依据；历史记录注明已被哪条结论替代。不能只在长报告末尾追加一句修正，让旧“未知”继续驱动下一轮任务。

续接时若计划的开放状态与 Fact 内容冲突，先读正式命题、版本和假设解决冲突；不自动信任笔记，也不把题名命中当作已覆盖。已接纳正确 Fact 的证据与历史不因贡献定位改变而编辑或删除。

笔记使用 UTF-8 和 Obsidian 兼容 Markdown，公式遵守 `$...$` 与 `$$...$$`。链接只指向实际存在的文件或标题。研究笔记可以包含猜想、失败、内部计算和协作者意见，但必须标明证据状态。

按[研究策略与定理提炼](research-strategy.md)在既有草稿和进展记录中保留值得解释的现象、候选局部定理、可能用途及假设边界。阶段回看简记为什么继续深入、转向应用或停止该路线；主目标推进与独立成果分开说明，不以 Fact 数量代替研究收益，也不增加固定状态表。

## Fact 阅读投影同步

Fact 阅读文件不得采用“用户读到时才生成”的惰性策略。每当当前研究流程接纳一个新 Fact 或新版本，主对话必须在报告任务完成前立即完成以下操作：

1. 在当前项目的 `Orpheus研究/Fact参考/` 创建或更新以自然标题命名的 Markdown 阅读投影；文件内保留固定 Fact ID、版本、状态、证据等级、接纳时间、依赖和正式审查链接。
2. 更新 `Orpheus研究/Fact参考/Fact索引.md`，使新版本按主题和依赖关系可浏览；同一 Fact 只保留一个入口，并明确当前版本。
3. 更新当前问题的 `相关Fact.md` 或 `提交与审查.md`，记录本次接纳结果及其与问题的关系。

只有 Fact 接纳和上述项目笔记同步都成功，才能把整条研究流程报告为完成。若 Fact 已接纳但项目文件写入失败，必须明确报告“Fact 已接纳、阅读投影待同步”，在 `Orpheus研究/Fact参考/同步待办.md` 记录 Fact ID、版本和失败原因，不能把失败隐藏成成功。

Orpheus 不使用后台服务扫描所有关闭的项目。每次在一个项目中开始或恢复 Orpheus 工作时，先把该项目的 Fact 索引与安装目录中的全部正式 Fact 目录核对，补齐项目关闭期间产生的新 Fact、版本变化、撤销和依赖失效状态；只有 `ACTIVE` Fact 可作为正式依赖引用。这一步是恢复同步，不以用户是否准备阅读某条 Fact 为条件。

### 结构初始化与机械同步

需要批量初始化或核对工作区时，可运行插件内的 `plugins/orpheus/scripts/sync_workspace.py`：

在已安装插件目录中运行（不要把仓库源码相对路径复制到缓存插件环境）：

```text
python scripts/sync_workspace.py check --workspace <项目根>
python scripts/sync_workspace.py sync --workspace <项目根>
python scripts/sync_workspace.py sync --workspace <项目根> --dry-run
python scripts/sync_workspace.py sync --workspace <项目根> --fact-id <新Fact ID> --version <版本>
```

脚本会从当前插件目录的 `.mcp.json` 读取 `orpheus-fact` 的绝对 stdio 入口，并由该入口反推出正式仓库；`--repo <仓库根>` 可显式覆盖并用于隔离测试。

脚本从仓库正式 `facts/` 读取 Fact 的版本和实际状态，并通过 `.mcp.json` 所在仓库定位来源；它只维护 `Orpheus研究/` 的目录、索引和自然标题阅读投影，不写入 `facts/`、`reviews/` 或 `candidates/`。新 Fact 接纳后使用 `--fact-id` 与 `--version` 只更新该投影和索引条目；开始或恢复项目时再运行不带筛选的完整 `check/sync`，核对撤销、失效和关闭期间的变化。新建投影完整复制 canonical Fact 正文；完整 `check` 会检测证明正文缺失或摘要替代，也会检查 `papers/` 下原文是否有同 stem sidecar，并验证登记目标存在且内容未变化；迁移旧问题时保留正文并修正标准文件名和链接；已有投影中的用户批注保留。脚本是结构与投影的确定性机械辅助，不代替 Codex 写研究内容、判断数学正确性或接纳 Fact。

`sync_workspace.py sync` 只初始化项目根 `papers/`，`check` 在缺失时报告问题；它不联网、不下载、不移动或覆盖用户文献。检查支持纯路径登记、硬链接登记和手动原文加 sidecar。脚本会为缺少完整性摘要的真实文件自动生成 sidecar 字段；已有摘要与当前文件不一致时报告 `PAPER_HASH_MISMATCH`，保留人工复核边界，不自动覆盖旧摘要。缺失原文报告 `MISSING_MANUAL_ORIGINAL` 或对应登记目标缺失；没有 `storage_mode` 的旧 sidecar 仍按兼容规则检查。问题级 `文献与证据.md` 只记录阅读、核查和引用关系。正式 `sources` 必须包含完整 citation 和精确 locator；本地路径与笔记链接只能留在工作区记录。

## 证据与正式引用

研究过程中可以参考当前项目笔记和通过 Fact 工具读取的内容。项目笔记用于上下文、路线和推导续接，不因写入 Markdown 就成为数学依据。

正式候选只能采用以下两类外部依据：

1. 已核实的外部文献，写入 `sources`，包含作者或机构、题名、版本或年份、定理／章节／页码等 locator，并在需要时保留短摘录。
2. 通过 `fact_get` 读取并核对的有效 Fact 精确版本，写入 `dependencies`，使用固定 `fact_id` 与整数版本。

本地研究笔记、聊天记录、子代理意见、搜索摘要和未核实网页不能写成正式 `sources` 或 `dependencies`。自足证明可以没有外部来源。用户给出的题面可以记录为问题来源，但不能冒充支持证明步骤的文献。引用 Fact 时同时检查状态、版本和内容是否真正支持当前步骤；普通 Obsidian 链接不能替代正式依赖字段。

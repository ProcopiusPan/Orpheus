# Orpheus 研究文档与 Obsidian 规范

## 1. 目标与适用范围

研究过程中形成的文档应当是用户能够直接阅读、在 Obsidian 中正确显示的 UTF-8 Markdown 文件。用户不需要从机器日志或 JSON 中重新拼装研究过程。

适用于问题说明、研究计划、进展、协作交接、证明草稿、候选命题、文献笔记、失败记录、验证报告、Fact 阅读副本和研究总结。默认使用自然的中文学术表达，保留必要的英文术语和原文引用。

计算代码、原始数据、文献 PDF 和服务内部数据库仍使用适合其用途的格式；相关结论、运行方法和证据解释必须有可读 Markdown 说明。结构化数据不替代用户文档。

本规范是输出与阅读约定，不增加研究流程状态机，不改变 Fact 的唯一硬边界。正式 Fact 的来源是 Git 中的 `facts/<fact-id>/vN.md` 与相邻机器元数据；Obsidian 阅读副本和研究笔记不能回写该目录。

Git commit 是候选哈希、精确依赖、审查报告和 Fact 版本的历史绑定。SQLite 可以从 Git Fact 重建查询索引，但不能作为事实来源。完整性异常先保存 `incidents/` 证据，恢复必须显式指定已知 commit 和路径。

远程保护能力取决于实际 Git 主机、仓库权限与仓库配置。只有已检查的远程设置或 CI 结果才能声明相应保护；远程备份、绿色 CI、本地检测和恢复能力分别记录，不相互替代。

## 2. 数学公式

- 行内公式统一使用 `$...$`，内容与分隔符之间不留首尾空格。
- 独立公式统一使用 `$$...$$`；起止 `$$` 各占一行，块前后留空行。
- 正文不使用 `\(...\)`、`\[...\]` 作为公式分隔符。
- `aligned`、`cases` 和矩阵等环境放在 `$$` 内，不在正文裸放 LaTeX 数学环境。
- 公式不放在代码围栏中代替渲染；展示源码语法时才使用代码样例。
- 引用块和 callout 内的公式，每行保留 `>` 前缀，包括空行和公式分隔符。
- 使用通用数学命令；自定义记号在文中解释，避免依赖未提供的全局宏或第三方插件。
- 不对代码、路径或引用原文做不加区分的分隔符全局替换。

行内示例：若 $n\in\mathbb{N}$，则 $n^2\geq 0$。

独立公式示例：

$$
\begin{aligned}
(a+b)^2 &= a^2+2ab+b^2,\\
(a-b)^2 &= a^2-2ab+b^2.
\end{aligned}
$$

引用块示例：

> [!note] 完整陈述适用条件
> 对任意实数 $x$，有
>
> $$
> x^2\geq 0.
> $$

## 3. 用户可读性

- 使用有意义的标题与文件名，避免仅以任务 ID 命名阅读入口。
- 实质研究文档先说明研究问题、当前结论和未解决事项；短笔记不强制套完整模板。
- 解释公式中的对象、假设和用途，不只堆公式或内部字段。
- 区分猜想、候选、条件结论、反例、模型审查通过与形式化检查；执行成功不等于数学成功。
- 证明具有清晰的论证顺序，关键引理与缺口使用稳定、明确的标题。
- 失败记录说明方法、失败位置、得到的认识和可能下一步。
- 协作记录保留有用结果、证据与分歧，不要求输出模型私有思维链或逐条内部调用日志。
- 验证报告包含摘要、逐项发现、引用核对和修补建议；机器 verdict 不替代正文。
- 候选摘要、Fact ID、版本和验证运行 ID 放在简短元数据区，正文围绕数学内容展开。

## 4. Obsidian 链接与引用

### 笔记之间的关系

- 合理使用双向链接连接问题、候选、证明、文献和失败路线；精确定位时使用标题链接或稳定块引用。
- 写链接前确认目标笔记及标题／块存在；同名笔记使用带文件夹的目标，避免歧义。
- 普通 Markdown 相对链接也可以使用，尤其是索引和需在其他阅读器中打开的材料。
- 库内链接相对研究库组织，不硬编码用户机器绝对路径；跨库 Fact 优先链接库内阅读副本，并保留服务身份。
- 适度嵌入短命题和关键结论；完整证明应可独立阅读，避免循环嵌入和过深嵌套。
- 不用不存在的笔记链接充当占位符，待研究主题先写为普通文字。

### 文献与证据

- 外部文献使用描述性链接，记录作者、题名、年份和可得的 DOI／arXiv／原始来源。
- 定理引用写明编号、页码或章节以及核对的版本；已有文献笔记时同时链接该笔记。
- 合理使用脚注承载补充来源；关键假设、科学限制和证明缺口留在正文。
- 摘录原文使用引用块并注明出处，自己的解释与摘录分开。
- 普通笔记链接只帮助阅读，不等于正式 Fact 依赖；候选提交仍需精确 Fact ID 和版本。

### 其他功能

- callout 用于结论、限制、疑问和反例，不为每段文字加框。
- 标签、aliases、YAML 属性按需要使用，不强制草稿填写大量属性。
- YAML 保持有效语法；多行公式和复杂数学内容放正文。
- 优先使用内置能力，不要求 Dataview、Templater 等第三方插件才能理解文档。
- 表格用于比较；长证明和多行公式移到表格外，避免分隔符破坏公式。
- 内容增多时维护简短索引，连接问题、进展、候选、Fact 和主要文献。索引是阅读导航，不是机器状态权威。

## 5. Fact 与验证报告的阅读副本

用户应能在 Obsidian 阅读正式 Fact 和验证报告，无需仅通过 MCP 才能看到正文。

- 接纳后提供对应版本的 Markdown 副本，完整复制 canonical Fact 的命题、证明、来源和精确依赖，并保留验证报告链接；证明副本不能用摘要替代正式证明。
- 拒绝、无法判定及执行错误也提供可读报告，区分数学问题与运行问题。
- 副本标明 Fact ID、版本、证据等级、导出时间和最后同步时的有效状态。
- 副本是阅读投影，不是第二个可写事实库；用户修改副本不能修改服务，修订需提交新候选。
- 离线副本无法保证反映最新撤销状态，应说明状态对应最后同步时间；同步后更新状态提示并保留历史。
- 同步不覆盖独立笔记中的批注。已被手工修改的导出文件发生冲突时保留双方内容，不静默覆盖。
- 正式验证以服务中的固定候选为准，不从可编辑副本反向认定验证身份。

采用简单的按需导出或现有工具返回产物；不建设双向同步数据库或后台研究管理器。

## 6. 维护检查

自动检查只处理格式和链接，不作为数学正确性判据。维护或交付时按适用范围执行以下检查：

- `research` 与 `review-proof` 的输出指导引用本规范；用户阅读交付物也遵循它。
- 阅读文档以 `.md` 落盘；验证报告不只有 JSON，重要研究进展不只留在对话里。
- 代码区域之外的公式分隔符、围栏配对及相对链接保持有效，不破坏合法源码样例。
- 双向链接、标题／块目标和脚注定义指向实际内容。
- 样例覆盖行内、多行、矩阵或分段公式、callout 内公式、脚注、链接和 Fact 状态。
- 若交付场景包含 Obsidian 渲染，另外检查公式显示和链接跳转；源码检查不替代渲染检查。
- 导出版本绑定、撤销后状态刷新、离线提示和手工批注保留。

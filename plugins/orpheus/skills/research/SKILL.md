# Orpheus 数学研究

主对话中的 Codex 负责统筹，自主选择证明、计算、反例、检索和按需协作。不同模型的一致意见不是证明。

## 研究目标与路线选择

用户明确要求完整计算、分类或解决总问题时保留该目标；否则默认追求陈述自然、解释机制清楚、在局部有力或可复用的结论。先确定足够有意义的最小成果，不默认研究整个对象、全部参数或所有类型。

选择路线、发现新现象或反复深入同一技术链时，按[研究策略与定理提炼](../../references/research-strategy.md)比较定理目标、廉价探查、关键困难与独立用途。完整计算或分类须说明其必要性；精确化、扩大参数和增加 Fact 数都不自动成为下一步。

每个新问题启动时，以及探索中发现新结构、等价表述或关键机制时，都按[文献探索与分析](../../references/literature-analysis.md)检索已有工作，再决定主要证明或计算投入。检索既覆盖原问题，也按对象的定义、公理、运算和不变量跨领域寻找不同名称下的同一结构、更强定理及可复用方法。Leader 据此明确已有结果覆盖了什么、桥接还缺什么、当前工作贡献在哪里；不要等证明完成才定位相关工作。续接时复用已记录的检索，只补查新增结构和缺口。

局部定理可以作为独立成果，不必服务原总目标。技术引理仍可及时保存；研究价值决定后续投入，证明正确性决定接纳。定理提炼与路线回看是研究工作，不增加提交前模型审计或 Fact 接纳关卡。

## 角色与编排

以下是逻辑角色，不是插件 manifest 中注册的固定代理。若当前 Codex 环境支持项目或个人级自定义代理，可参考
[`references/agent-orchestration.md`](../../references/agent-orchestration.md) 及其中的模板；模板只有复制到
项目 `.codex/agents/` 或个人 `~/.codex/agents/` 后才会被 Codex 加载。若环境不支持角色文件，Leader
直接用同样的职责说明启动普通子代理即可。

- **researcher**：发现现象，提炼自然假设下的结构定理、判据、界、反例或方法，并解释其用途与失败边界。不要把未限定的探索自动扩成完整计算或分类。沿同一路线继续时，复用已有 researcher
  线程并发送 follow-up；开辟新路线时可新建线程并按需要继承有限或全部上下文。无论继承多少对话，都必须
  读取持久问题笔记和相关 ACTIVE Fact；对话历史不能替代持久记录。
- **verifier**：只对一个已固定、不可变的 Candidate 做独立冷审。每个 Candidate（包括每个修订版）都必须
  新建 verifier 线程并使用 `fork_turns=none`；不得复用 researcher 或旧 verifier。证据白名单只有固定
  Candidate、其中列出的精确 ACTIVE Fact 版本、正式 sources 和绑定附件。共享工作区可见不等于可以作为证据。
- **compute**：重放或设计已限定输入、范围和输出的确定性计算，提交脚本、报告和机器可读结果。不得把
  有限枚举、有限商或抽样结果外推为全称数学结论。
- **reader**：围绕研究目标梳理文献的整体贡献、相关与更强结果、假设和适用边界，整理版本、locator、依赖及
  对研究路线的影响；不裁决 Fact 接纳，也不把阅读摘要提升为正式来源或 Fact。

### 模型选择

Orpheus 不为上述角色规定具体模型或推理强度。Leader 必须遵守用户在当前请求中明确指定的模型要求；用户
未指定时，启动子代理时省略模型和推理强度覆盖参数，让 Codex 按用户配置、全局默认值或父代理继承规则决定。
用户可以按角色分别向 Leader 指定不同模型；这种选择属于当前任务调度，不写入插件规则或角色模板。

### 上下文边界与槽位

researcher 的连续工作优先通过同一线程的 follow-up 保留路线上下文；新 researcher 只继承完成任务所需的
上下文，并始终重新读取持久笔记和 ACTIVE Facts。compute 与 reader 默认只接收最小必要上下文。

正式 verifier 必须保持冷启动：新线程、`fork_turns=none`、固定证据入口、只读审查职责。Verifier 的报告不能
替代 Leader 对候选依赖、版本和绑定附件的宿主核对。并发由宿主当前可用的协作容量决定；启动研究代理前查看
活动线程，给新 verifier 预留可用容量，并在达到宿主边界时停止扩张。研究代理交付后不继续占用它做无关路线，
只有确需返工时才续接。

## 可靠结论及时保存

研究一旦得到**证明完整、边界明确、可独立引用**的局部结论，就先提交并冷审，不要等总问题解决。可提交引理、命题、条件性结论、显式正反例或精确计算结论；猜想、数值观察和未完成推导只写入笔记。

一个候选承载一个可独立引用的结论单元。小 Fact 指短而完整的数学义务，不是把同一次计算的每个函数、循环或输出各拆一次。出现下列任一情况时才拆分：

- 证明包含可单独陈述并被后续复用的中间引理；
- 审查者必须分别核验多种独立算法、分类桥接或外部定理；
- 结论的一部分失败时，其余部分仍可能独立成立；
- 候选把枚举、代数构造、分类及最终应用串成一整条长链。

最终定理可以依赖多个已接纳 Fact，但不要把整条依赖链重新塞进一个候选。尚未接纳或被打回的候选只能作为暂定材料，不能成为后续正式依赖。

## 研究循环

1. 开始或恢复问题时，读取问题笔记、相关有效 Fact 和已有检索记录；新问题先广泛检索，恢复问题补查新线索，再选择投入可控、收益明确的近期定理或探索问题。
2. 出现新现象、实质进展、失败原因或协作结果时，在阶段回看中比较继续深入、提炼机制、寻找用途和发展旁支的价值；发现新结构或机制时立即触发跨领域检索，更新贡献定位，并及时写入用户项目的 Obsidian 笔记。
3. 形成一个小结论后，只做一次廉价边界检查：断言量词没有超出证据，Fact 依赖有效且版本精确，外部来源有 locator；计算候选同时含实际脚本、用户可读报告以及机器可读结果或证书；字段满足 schema。它不是新的模型审计；通过后立即调用 `candidate_submit`。
4. `SUBMITTED` 后立即启动一个不继承研究推导的新冷审查者，但不要立刻停下来等待。Leader 继续推进不依赖该候选的路线、文献和计算；可以探索依赖该候选的推论，但必须标为暂定，不能提交或写入正式依赖。
5. 在完成一项独立工作、准备提交下一个候选、暂停、交接或结束任务时检查在审结果。宿主核对报告绑定后记录审查；`PASS` 且没有错误或未解决缺口时优先立即接纳，不再增加第二轮审计；`REJECT` 或 `INCONCLUSIVE` 时不得接纳，由 Leader 优先判断能否修复，否则换路线。接纳结果中的 `remote_sync.status` 必须同时报告：`SYNCED` 表示已备份到 `origin/main`，`REMOTE_PENDING` 表示 Fact 已在本地接纳但远端待同步，`NOT_CONFIGURED` 表示没有远端。后两种状态不得说成已经上传；可通过幂等地再次接纳同一候选重试普通 push。
6. 修订必须使用新请求键和新冷审，旧候选与旧报告保持不变。接纳后立即同步当前项目的 Fact 阅读投影、索引和问题记录。

研究协作和在审候选都遵守宿主当前可用的并发边界。启动研究协作或提交候选前先查看现有代理和审查状态，
为新冷审保留所需容量；达到边界后先回收已有结果，再继续安排新工作。不要通过重复提交、复用旧 verifier
或无限创建线程绕过容量限制。研究代理交付后不继续占用它做无关路线，确需返工时才续接。

在审候选也遵守宿主当前可用的审查容量。达到边界后先回收已有 verdict，再提交新的候选。若创建审查者返回线程
上限，暂停创建新的研究代理，在下一项独立工作结束时按同一请求重试一次；候选保持 `SUBMITTED`，不得重复提交。
只有没有可推进的独立工作时才等待 Verifier。研究协作者的复算和意见属于研究材料，不是提交前审计，也不能代替冷审查。

## 证明与证据

候选证明必须能独立逐步核查。展开非平凡对象变换、等式、量词、分情况、边界以及引用的适用条件；不能用“显然”“同理”或计算摘要替代关键论证。

正式来源只包括已核对且有精确 locator 的外部文献；正式依赖只包括已读取并核对的有效 Fact 精确版本。本地笔记、网页摘要、脚本路径和子代理意见不能冒充 `sources` 或 `dependencies`。自足证明允许没有外部来源。字段和工具约定见[Fact 工具与证据](../../references/facts.md)。

确定性计算优先形成一条可复用链：算法及正确性证明作为算法 Fact；一次确定输入、环境和输出作为运行 Fact，依赖算法 Fact，并把实际脚本、用户可读报告、机器可读结果或证书全部绑定进 Fact；从输出推出的数学命题再依赖运行 Fact。只保存工作区路径或文字摘要不算保存实验结果。算法与运行也可在内容很短且紧密时合成一个 Fact，不按程序阶段机械拆分。首次审查核对算法与命题的对应，必要时重放；以后直接精确依赖内容匹配的已有 Fact，不再重复运行或重复附同一脚本。

不要在候选、报告或人工 manifest 中抄写文件哈希、字节数或候选摘要。Fact 服务自动绑定内容并维护完整性元数据；研究者只需提交真实附件和陈述其数学含义。带附件时优先调用 `candidate_submit_files` 传递本地路径，让服务直接读取文件；不要用 `Get-Content` 或类似命令把大附件送入对话，再内嵌到工具参数。

反复使用的外部定理应在首次严查原文、版本、locator 和适用条件后形成文献 Fact。后续候选若范围完全落在该 Fact 内，只引用其精确版本；只有超出范围、版本变化或该 Fact 被质疑时才重查原文。

找到有用的文献结果后，按[文献探索与分析](../../references/literature-analysis.md)梳理同篇论文的主要贡献、相关结果和可能更强的结论，比较完整假设与结论，并沿有价值的前置工作、后续推广或修正继续检索。Leader 根据这些内容更新已知研究范围、剩余问题和研究路线。引用已核实不等于论文已充分阅读；复用文献 Fact 只免去相同引用的重复核验，不限制新问题的扩展阅读。用户明确限定为单条引用核验时遵守该范围。

需要文献时，若当前环境已配置 Zotero，可用它搜索、读取和登记；未配置时直接使用项目 `papers/`、合法检索和可核验来源，
不因缺少 Zotero 阻塞研究。实际用于研究的条目应登记到项目 `papers/`，问题级 `文献与证据.md` 记录精确阅读位置。只有实际核对的原文
才能进入候选来源。具体目录、登记和同步规则见[项目工作区与研究笔记](../../references/workspace-notes.md)。

## 边界与记录

用户选定的本地项目保存 `Orpheus研究/` 和共享 `papers/`；安装目录保存候选、审查和正式 Fact。用户文档遵守[Obsidian 规范](../../references/obsidian.md)，公式使用 `$...$` 与 `$$...$$`。

AI 不得直接编辑或删除 `facts/`、`reviews/`、manifest 或历史版本。正式路径只有候选提交、绑定冷审、显式接纳。完整性异常先保存 incident；恢复或 Git revert 默认只预览，只有用户明确指定 `--apply` 才执行。AI 审查通过只标记 `AI_REVIEWED`。

结束或交接前记录当前结论、未解决问题、候选或 Fact ID、必要文献和下一步，使研究能够从文件继续。
